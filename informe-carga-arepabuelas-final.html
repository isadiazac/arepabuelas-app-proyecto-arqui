Informe de Pruebas de Carga

Aplicación Web "Arepabuelas"

Fecha: 19 de noviembre de 2025

1. Introducción

Este informe documenta las pruebas de carga ejecutadas sobre la aplicación Arepabuelas mediante la herramienta k6. El objetivo fue medir el comportamiento del sistema bajo múltiples usuarios concurrentes, incluyendo autenticación y acceso a rutas protegidas.

2. Escenario de pruebas

  • Usuarios virtuales (VUs): 10
  • Duración: 30 segundos
  • Prueba: login y acceso a /api/users/active con JWT

3. Resultados esperados

  • El login debe responder con 200 OK.
  • Debe recibirse un token JWT válido.
  • El endpoint protegido debe responder con 200 OK al recibir el token.

4. Resultados observados

Durante la ejecución de la prueba, el backend comenzó a responder con códigos 429 Too Many Requests después de varios intentos de login.

Esto indica que el backend cuenta con mecanismos de rate limiting, lo cual es una buena práctica de seguridad, pero impide pruebas masivas sin configuración previa para permitirlas.

5. Recomendaciones

  • Configurar el sistema de autenticación para permitir ciertas IPs de prueba sin límite o con límites más altos durante las pruebas de carga.
  • Incluir una pausa (sleep) entre inicios de sesión o distribuir logins previos y luego solo medir las rutas protegidas.
  • Separar pruebas de login de pruebas de endpoints autenticados para no sobrecargar el login.

6. Conclusiones

El sistema respondió correctamente inicialmente, pero las defensas antiabuso bloquearon los intentos posteriores. Esto demuestra una configuración adecuada para producción, pero se recomienda ajustar temporalmente dichos parámetros para entornos de prueba controlados.

5. Primera ejecución: resultados exitosos

Durante la primera ejecución del script con 50 VUs simultáneos y múltiples escenarios, se observó lo siguiente:

  • Frontend responde 200: ✓ 100% (todas las respuestas fueron exitosas)
  • Login responde 200: ✗ 16% (debido a errores intermitentes por volumen)
  • Token presente: ✗ 16%
  • Acceso a /users/active: ✗ 0% (por fallos en login)

El frontend demostró buena capacidad de respuesta y estabilidad. Sin embargo, el backend presentó problemas de capacidad para manejar múltiples inicios de sesión simultáneos, con respuestas 429 antes de finalizar el escenario.

6. Segunda ejecución: límites de tasa alcanzados

Durante la segunda ejecución del script con 10 VUs durante 30 segundos, el backend respondió consistentemente con el código 429 Too Many Requests debido al mecanismo de rate limiting habilitado en el API.

Esto indica que la protección contra abuso está funcionando correctamente, limitando la cantidad de inicios de sesión desde una misma IP. Sin embargo, para pruebas de carga controladas, se recomienda desactivar temporalmente este middleware o configurar una mayor tolerancia.

  • Login responde 200: ✗ 0% (todas las solicitudes bloqueadas con 429)
  • Token presente: ✗ 0% (no se emitió ningún token)
  • Acceso a /users/active: ✗ 0% (no se ejecutó por fallo en login)
