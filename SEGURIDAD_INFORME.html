Informe de Pruebas de Seguridad y Carga

Aplicación Web "Arepabuelas"

Autores: Ana María Cordero, Pablo Boada, Isabela Díaz

Fecha: 19 de noviembre de 2025

1. Introducción

El presente informe documenta las pruebas de seguridad realizadas sobre la aplicación web Arepabuelas, desarrollada con un frontend en React, un backend en Node.js y una base de datos PostgreSQL, todos ejecutándose en un entorno contenerizado con Docker.

El objetivo principal es identificar vulnerabilidades técnicas, evaluar la exposición de servicios en red y proponer mitigaciones concretas alineadas con buenas prácticas de seguridad web. Para ello se emplearon herramientas de análisis dinámico y de infraestructura, específicamente OWASP ZAP, Nikto y Nmap.

2. Arquitectura del sistema

La aplicación Arepabuelas adopta una arquitectura cliente–servidor distribuida, desplegada mediante un stack Docker donde, al levantar el entorno, se habilitan tres servicios diferenciados:

  • Frontend: Aplicación React sirviendo la interfaz web, expuesta en http://localhost:3000.
  • Backend: API REST construida con Node.js/Express, expuesta en http://localhost:4000.
  • Base de datos: PostgreSQL, accesible únicamente desde el backend dentro de la red interna de Docker.

Esta estructura responde a un modelo clásico de tres capas:

  • Capa de presentación: el frontend React, que maneja la UX y las interacciones del usuario.
  • Capa de lógica de negocio: el backend Node/Express, donde se implementan las reglas de negocio, autenticación y acceso a datos.
  • Capa de persistencia: la base de datos PostgreSQL, responsable del almacenamiento permanente de la información.

Desde la perspectiva del modelo C4, el sistema puede describirse así:

  • Contexto: Un sistema web que permite la gestión de funcionalidades internas de Arepabuelas, accedido por usuarios administradores a través del navegador.
  • Contenedores: tres contenedores (frontend React, backend Node, DB PostgreSQL) comunicados por una red interna Docker.
  • Componentes: en el backend se pueden distinguir controladores (rutas), servicios de dominio y componentes de acceso a datos; en el frontend, vistas/páginas y componentes React que consumen la API.
  • Vista física: todos los contenedores se ejecutan en un mismo host, aislados pero coordinados por Docker Compose.

3. Metodología de pruebas

Para evaluar la seguridad de Arepabuelas se siguió una metodología basada en el uso de herramientas especializadas y en el análisis manual de los resultados:

  • OWASP ZAP: se utilizó para realizar un escaneo activo de la aplicación, incluyendo: crawleo de http://localhost:3000 y http://localhost:4000, identificación de cabeceras de seguridad faltantes, revisión de políticas CSP y análisis de posibles problemas de configuración.
  • Nikto: se ejecutó contra los puertos 3000 (frontend) y 4000 (backend) con el fin de detectar configuraciones inseguras a nivel de servidor web (cabeceras, archivos potencialmente accesibles, etc.).
  • Nmap: se realizó un escaneo de puertos y detección de servicios en localhost sobre los puertos 3000 y 4000, incluyendo fingerprint de versiones y respuestas HTTP devueltas.

Nota: Las pruebas de carga se planearon con K6, pero en este informe se documentan únicamente las pruebas de seguridad (ZAP, Nikto, Nmap).

4. Escaneo OWASP ZAP

4.1 Resumen de hallazgos

El reporte de OWASP ZAP sobre http://localhost:3000 y http://localhost:4000 indica un total de 20 alertas, distribuidas en:

  • Riesgo Medio: 6 alertas (principalmente relacionadas con Content Security Policy y configuraciones CORS).
  • Riesgo Bajo: 4 alertas (exposición de información en cabeceras como Server y X-Powered-By, cabeceras de seguridad faltantes).
  • Informativas: 10 alertas (detección de tecnologías, gestión de sesión, aplicación web moderna, etc.).

Entre los tipos de alerta más relevantes se destacan:

  • CSP: Directiva Wildcard / unsafe-inline / no configurada: problemas con la cabecera Content-Security-Policy.
  • Configuración incorrecta cross-domain: uso de Access-Control-Allow-Origin: * en el backend.
  • Falta de cabecera Anti-Clickjacking: ausencia de X-Frame-Options en algunas respuestas (especialmente frontend).
  • Falta encabezado X-Content-Type-Options: posibilidad de que el navegador “adivine” tipos MIME.
  • Divulgación de versión: cabeceras como Server: nginx/1.28.0 o tecnologías detectadas (Express, Vite, etc.).

4.2 Explicación e interpretación del escaneo ZAP

El escaneo de ZAP muestra que la aplicación ya incluye algunas defensas importantes a nivel de backend, como una política CSP relativamente estricta y cabeceras como Strict-Transport-Security, X-Frame-Options y X-Content-Type-Options en ciertas respuestas del API. Sin embargo, la configuración actual no es consistente entre todos los endpoints ni entre frontend y backend, y en algunos casos la política CSP permite 'unsafe-inline' en style-src o deja directivas sin definir adecuadamente. Esto implica que, aunque el sistema tiene una base razonable de seguridad, todavía existe una superficie de ataque relevante para XSS, clickjacking y otros ataques basados en contenido. En conjunto, los hallazgos de ZAP apuntan a que la principal debilidad del sistema no está en vulnerabilidades de negocio específicas, sino en la configuración incompleta o inconsistente de cabeceras y políticas de seguridad a nivel de HTTP.

5. Escaneo Nikto – Backend (puerto 4000)

5.1 Resumen de hallazgos

El escaneo Nikto contra localhost:4000 arrojó los siguientes puntos relevantes:

  • Se detectó la cabecera Access-Control-Allow-Origin: *, lo cual indica una política CORS muy permisiva.
  • Se reportó ausencia de X-Content-Type-Options en algunas respuestas analizadas.
  • Se encontraron cabeceras de rate limiting (X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset), lo cual es bueno para proteger el API de abuso.

5.2 Explicación e interpretación del escaneo Nikto (backend)

El resultado de Nikto confirma que el backend expone una API con cierto nivel de robustez (incluyendo rate limiting), pero mantiene una política CORS excesivamente abierta al permitir el acceso desde cualquier origen (*). Esto puede ser aprovechado por sitios de terceros maliciosos para realizar peticiones a la API en nombre del usuario. Además, la ausencia de X-Content-Type-Options en algunas rutas puede permitir que el navegador interprete contenido de forma no intencionada, especialmente si en el futuro se sirven archivos no estrictamente JSON. En conjunto, el backend no presenta vulnerabilidades críticas directas, pero su configuración actual requiere endurecimiento para alinearse con buenas prácticas de seguridad de APIs.

6. Escaneo Nikto – Frontend (puerto 3000)

6.1 Resumen de hallazgos

El escaneo Nikto sobre localhost:3000 reportó:

  • Ausencia de la cabecera X-Frame-Options (protección anti-clickjacking).
  • Ausencia de la cabecera X-Content-Type-Options.
  • Múltiples entradas del tipo “Potentially interesting backup/cert file found” para rutas como /backup.tar, /database.war, /localhost.pem, etc. En la práctica, Nikto suele probar estas rutas con peticiones HEAD; normalmente devuelven 404, pero se listan como potencialmente interesantes.

6.2 Explicación e interpretación del escaneo Nikto (frontend)

Los resultados de Nikto en el frontend son coherentes con lo observado en ZAP: el servidor que sirve la aplicación React (en este caso nginx) no está configurado con las cabeceras de seguridad recomendadas por OWASP. La ausencia de X-Frame-Options permite que la aplicación sea embebida en iframes de terceros, facilitando potencialmente ataques de clickjacking. La falta de X-Content-Type-Options deja una puerta abierta para confusiones de tipo MIME en el navegador. Por otro lado, las decenas de rutas de “archivos de backup” reportadas son, más que nada, un aviso para verificar que no existan realmente archivos de respaldo en el directorio público. En un entorno bien configurado, estas rutas deben devolver 404 y no representar una vulnerabilidad real, pero vale la pena revisar que no se suban accidentalmente artefactos de despliegue o copias de bases de datos al directorio servido por nginx.

7. Escaneo Nmap

7.1 Resumen de hallazgos

El comando ejecutado fue similar a:

nmap -sV -A -p3000,4000 localhost

Los resultados principales fueron:

  • Puerto 3000/tcp: abierto, servicio HTTP con nginx 1.28.0.
  • Puerto 4000/tcp: abierto, servicio HTTP personalizado (Node/Express) que responde con códigos como 429 Too Many Requests y cabeceras de seguridad (CSP, HSTS, X-Frame-Options, etc.).
  • El host corre sobre una distribución Linux (kernel 5.x/6.x según fingerprint), sin otros puertos abiertos en el rango analizado.

7.2 Explicación e interpretación del escaneo Nmap

El escaneo de Nmap confirma que la superficie de exposición en red está limitada a los puertos esperados (3000 y 4000), lo cual es positivo. Sin embargo, también revela información sensible como la versión exacta de nginx/1.28.0 en el frontend. Este tipo de datos puede ser aprovechado por un atacante para buscar vulnerabilidades conocidas específicas de esa versión del servidor. Por otro lado, las respuestas del backend muestran una configuración relativamente avanzada de cabeceras de seguridad, junto con mecanismos de rate limiting, lo que indica un esfuerzo por proteger la API. Aun así, desde el punto de vista de hardening, se recomienda ocultar banners de versión cuando sea posible y revisar periódicamente que los servicios expuestos no tengan CVEs abiertas en esas versiones.

8. Mitigaciones propuestas

A partir de los hallazgos de ZAP, Nikto y Nmap, se proponen las siguientes acciones de mitigación:

  • Configurar correctamente Content-Security-Policy (CSP): eliminar 'unsafe-inline' en style-src cuando sea posible, limitar img-src, font-src y demás directivas a orígenes estrictamente necesarios.
  • Unificar cabeceras de seguridad en frontend y backend: asegurar que todas las respuestas incluyan (según aplique) X-Frame-Options o frame-ancestors en CSP, X-Content-Type-Options: nosniff, Referrer-Policy restrictiva y Strict-Transport-Security cuando se use HTTPS.
  • Endurecer CORS: reemplazar Access-Control-Allow-Origin: * por una lista explícita de orígenes confiables (por ejemplo, el dominio real del frontend en producción).
  • Revisar archivos expuestos: confirmar que en el directorio público del frontend no existan archivos de backup, certificados, .war, .tar, .tgz, etc.
  • Reducir información en banners: configurar nginx y otros servidores para no exponer versiones exactas en la cabecera Server.
  • Revisar autenticación y sesiones: asegurar que las cookies de autenticación estén marcadas como HttpOnly, Secure y con SameSite apropiado (por ejemplo, Strict o Lax).
  • Pruebas posteriores: una vez aplicadas las mitigaciones, repetir los escaneos de ZAP y Nikto para verificar que las alertas relacionadas a cabeceras y políticas hayan disminuido.

10. Escaneo Trivy (Contenedores)

10.1 Resultados por servicio

  • Backend (Node.js): Trivy reportó varias vulnerabilidades con niveles de riesgo medio y alto, principalmente en dependencias de Node utilizadas en el contenedor. Algunos paquetes críticos requieren actualización o reemplazo (por ejemplo, versiones antiguas de Express o bibliotecas de logging).
  • Frontend (React): el escaneo detectó vulnerabilidades menores, en su mayoría relacionadas con dependencias de desarrollo (devDependencies), lo cual reduce su impacto en producción.
  • Base de datos: Trivy identificó varias CVEs en la imagen base de PostgreSQL (por ejemplo, en paquetes del sistema operativo), pero ninguna directamente explotable en el contexto actual. Se sugiere usar imágenes actualizadas con menor superficie de ataque.

10.2 Interpretación y recomendaciones

El análisis de Trivy pone de manifiesto la importancia de mantener actualizadas las imágenes y dependencias de los contenedores. En particular:

  • Evitar imágenes :latest sin control de versiones, optando por versiones específicas y estables.
  • Aplicar actualizaciones de seguridad periódicas en paquetes del sistema dentro de los contenedores (por ejemplo, usando imágenes oficiales actualizadas).
  • Reducir el uso de dependencias innecesarias, sobre todo en producción.
  • Automatizar el análisis de imágenes como parte del proceso CI/CD, para detectar vulnerabilidades antes del despliegue.

9. Conclusiones

La aplicación Arepabuelas presenta una arquitectura moderna y modular, apropiada para su contexto de uso, con una separación clara entre frontend, backend y base de datos en contenedores Docker. Las pruebas de seguridad realizadas con OWASP ZAP, Nikto y Nmap no revelan vulnerabilidades críticas de negocio o fallos graves como inyecciones directamente explotables; sin embargo, sí ponen de manifiesto debilidades importantes en la configuración de seguridad a nivel de cabeceras HTTP, políticas CSP y CORS.

Estas debilidades, de no corregirse, podrían facilitar ataques como XSS, clickjacking o abuso del API desde orígenes no autorizados. La buena noticia es que la mayoría de los problemas identificados pueden mitigarse mediante ajustes de configuración relativamente sencillos en nginx y Express, junto con una revisión de los headers generados por el backend.

Como trabajo futuro, se recomienda integrar estas configuraciones de seguridad dentro del ciclo de desarrollo (por ejemplo, como parte de la configuración por defecto del proyecto) y automatizar los escaneos de ZAP/Nikto en un pipeline de CI/CD para detectar regresiones de seguridad de manera temprana.
